# Типизированные параметры профилей и бюджеты исполнения

Дата: 2026-06-24

Статус: утвержденный проект решения

## Цель

Расширить существующий каталог инструментов так, чтобы профиль определял:

- типы, значения по умолчанию и ограничения параметров;
- жесткие потолки продолжительности, количества целей, скорости и
  параллельности;
- итоговые проверенные параметры и эффективный бюджет до создания задания.

Изменение не вводит новую службу и не переносит политику в раннеры.
`ActionService`, каталог и policy-слой остаются границей создания управляемого
действия.

## Область первого среза

Первый срез включает:

1. декларативные схемы параметров в профилях `pipeline.yaml`;
2. декларативные бюджеты профилей;
3. применение значений параметров по умолчанию;
4. проверку типов, диапазонов и перечислений;
5. вычисление эффективного бюджета;
6. блокировку недопустимого запроса до создания `job`;
7. сохранение проверенных параметров и эффективного бюджета с действием;
8. передачу проверенных значений через `ToolInvocation`.

Первый срез не включает:

- распределенный ограничитель скорости;
- глобальные квоты программы или кампании;
- динамическое перераспределение бюджета;
- автоматическое планирование кампаний;
- отдельные таблицы параметров и бюджетов;
- новую службу исполнения.

Эти возможности добавляются позднее поверх того же контракта эффективного
бюджета.

## Декларативная модель

Профиль каталога получает `options` и `budgets`.

```yaml
profiles:
  safe-crawl:
    label: Safe crawl
    safety_level: safe_active
    options:
      depth:
        type: integer
        default: 2
        minimum: 1
        maximum: 5
      js_crawl:
        type: boolean
        default: true
      headless:
        type: boolean
        default: false
      timeout:
        type: integer
        default: 60
        minimum: 1
        maximum: 120
    budgets:
      max_duration_seconds: 120
      max_targets: 20
      rate_per_second: 10
      concurrency: 2
```

`allowed_options` остается временно поддерживаемым входным форматом для
совместимости. При наличии `options` список разрешенных имен выводится из его
ключей. Одновременное объявление противоречащих `allowed_options` и `options`
отклоняется при загрузке manifest.

## Схема параметра

Поддерживаемые типы первого среза:

- `integer`;
- `number`;
- `boolean`;
- `string`.

Поля:

- `type` — обязательно;
- `default` — необязательно;
- `minimum` и `maximum` — только для числовых типов;
- `enum` — необязательный непустой список разрешенных значений;
- `required` — по умолчанию `false`.

Правила:

- значение по умолчанию проходит ту же проверку, что и пользовательское;
- `minimum` не может быть больше `maximum`;
- значения `enum` должны соответствовать объявленному типу;
- неизвестные параметры отклоняются;
- автоматическое преобразование строк `"10"` в число и `"true"` в
  логическое значение запрещено;
- обязательный параметр без значения и без `default` отклоняется.

## Бюджет профиля

Контракт бюджета:

```text
ExecutionBudget:
  max_duration_seconds: positive number | null
  max_targets: positive integer | null
  rate_per_second: positive number | null
  concurrency: positive integer | null
```

Все заданные значения должны быть положительными.

Профильный бюджет является жестким потолком. Запрос может передать
необязательное `budget` только для уменьшения лимитов.

Эффективное значение для каждого измерения:

```text
minimum(system_limit, profile_limit, requested_limit)
```

Из отсутствующих значений берутся только присутствующие пределы. Если не задан
ни один предел, используется системный предел. Отсутствие профильного значения
не означает бесконечный бюджет.

Системные потолки задаются настройками приложения. Для `concurrency`
используется существующий `ORCHESTRATOR_MAX_CONCURRENT`; для остальных
измерений добавляются отдельные обязательные настройки с консервативными
значениями по умолчанию. Конкретные значения фиксируются в плане реализации и
проверяются тестами конфигурации.

Попытка увеличить профильный или системный предел отклоняется с явной причиной,
а не молча обрезается. Это позволяет клиенту видеть, что запрос противоречит
политике.

## Публичный контракт действия

`ActionRequest` получает необязательное поле:

```text
budget: ExecutionBudgetRequest | null
```

После разрешения каталога действие содержит:

- `options` — итоговые проверенные параметры с примененными значениями по
  умолчанию;
- `effective_budget` — рассчитанный бюджет исполнения.

Пользователь не может прислать `effective_budget` напрямую.

`ToolInvocation` получает обязательный `execution_budget`. Рабочий узел и
раннер используют только этот проверенный контракт.

## Порядок обработки

```text
ActionRequest
  -> получить активный профиль каталога
  -> проверить и дополнить options
  -> вычислить effective_budget
  -> проверить capability/scope/risk/approval
  -> сохранить действие и решение
  -> создать job/run только для разрешенного действия
  -> передать options и execution_budget в ToolInvocation
```

Проверка параметров и бюджета выполняется до policy evaluation, поскольку
policy должна получать уже нормализованный запрос. Scope и approval по-прежнему
выполняются до создания `job`.

## Хранение

Первый срез использует существующие структуры:

- итоговые `options` сохраняются в `action_requests.request` и
  `action_request_options`;
- `effective_budget` сохраняется в `action_requests.metadata` и копируется в
  payload исходящего события;
- `runs.run_payload` получает бюджет при создании/планировании рабочего запуска.

Новая миграция и отдельные таблицы не нужны, пока бюджет не требует счетчиков
потребления и истории изменений. Будущие `campaign_budget_events` будут
ссылаться на этот исходный контракт.

## Исполнение

В первом срезе:

- `max_targets` проверяется до создания задания и повторно при разбиении целей;
- `max_duration_seconds` ограничивает timeout, передаваемый в раннер;
- `concurrency` ограничивает локальную параллельность рабочего узла;
- `rate_per_second` передается только раннерам с типизированным параметром
  скорости.

Если инструмент не поддерживает скорость, наличие `rate_per_second` остается
аудитным потолком и не превращается в произвольный аргумент командной строки.
Общий распределенный ограничитель скорости является следующим отдельным
этапом.

## Ошибки

Ошибки каталога при загрузке:

- неверная схема параметра;
- неверное значение по умолчанию;
- противоречие `allowed_options` и `options`;
- неположительный бюджет;
- неизвестный тип параметра.

Ошибки запроса:

- неизвестный параметр;
- неверный тип;
- значение вне диапазона;
- значение вне `enum`;
- отсутствует обязательный параметр;
- запрошенный бюджет превышает жесткий потолок;
- количество целей превышает эффективный `max_targets`.

Недопустимые параметры, бюджет или количество целей возвращают `422` до
создания action/job. Policy/scope/approval продолжают использовать существующие
статусы действий после успешной нормализации запроса.

## Безопасность

- Командоподобные имена параметров остаются запрещенными.
- Схема профиля не может объявлять `cmd`, `command`, `shell`, `exec`,
  `raw_command` и аналогичные ключи.
- Раннеры продолжают строить список аргументов и не принимают shell-строки.
- Запрос не может расширить профильный или системный бюджет.
- Все эффективные значения доступны для аудита.

## Совместимость

- Существующие профили с `allowed_options` продолжают загружаться.
- Для старых профилей типизированные значения по умолчанию отсутствуют;
  переданные значения проходят текущую проверку разрешенных имен.
- Профили переводятся на `options` постепенно, начиная с `httpx`, `katana`,
  `ffuf` и `naabu`.
- Формат snapshot меняет хеш каталога, но не требует ручного редактирования
  PostgreSQL.

## Проверки

Контракты manifest:

- схема принимает корректные типы, значения по умолчанию и бюджеты;
- неверные ограничения отклоняются;
- хеш snapshot меняется при изменении схемы или бюджета;
- materialized entry содержит схему и бюджет в `manifest_fragment`.

Контракты действия:

- значения по умолчанию применяются до policy;
- неизвестный или неверно типизированный параметр блокируется без `job`;
- запрос не может увеличить бюджет;
- количество целей не превышает `max_targets`;
- итоговые параметры и бюджет входят в event payload.

Контракты исполнения:

- `ToolInvocation` содержит эффективный бюджет;
- `httpx`, `katana`, `ffuf` и `naabu` получают проверенный timeout;
- `naabu` получает ограниченную скорость;
- рабочий узел применяет ограничение параллельности;
- построение команд остается shell-safe.

Полная проверка:

```powershell
.\.tmp_pytest\Scripts\python.exe -m pytest -q
```

## Критерий завершения

Первый срез завершен, когда каталог является источником истины для типов,
значений по умолчанию и потолков бюджета, недопустимый запрос не создает
`job`, а каждый разрешенный запуск получает сохраненные и аудируемые
`options + execution_budget`.
